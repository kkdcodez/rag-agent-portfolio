# Week 4 — 청킹 전략 (Chunking Strategy)

데이터 진단(`week4_data_diagnosis.md`)에서 나온 언어별 밀도 차이를 근거로, 실제 청킹 전략을 실험으로 결정한다. 감이 아니라 **변수를 하나씩 격리한 비교 실험**으로 크기·클렌징·로더를 판정한다.

## 1. 목적
"문서를 어떻게 잘라야 검색이 잘 되는가"를 결정한다. 진단이 좁혀준 후보 범위 안에서, 언어별 크기·노이즈 제거·파서를 각각 격리해 근거 있는 청킹 config를 확정한다.

## 2. 실험 히스토리 개요

| 버전 | 실험 대상 | 상태 | 결론 |
|---|---|---|---|
| v1 | 청킹 방식 A/B/C 탐색 | 완료 | 뭉뚱그린 비교의 한계 확인 → 변수 격리 필요 |
| v2 | 언어별 크기 격자 + 클렌징 | 완료 | **G2_ko4_en3 채택 / 클렌징 기각** |
| v3 | 로더 (PyMuPDFLoader vs pymupdf4llm) | 완료 | **PyMuPDFLoader 유지 / pymupdf4llm 기각** |

## 3. v1 — 초기 탐색과 그 한계

**진행 내용**: A(512/100), B(1000/200), C(언어별+클렌징) 세 방식을 10문항으로 비교.

**발견한 문제**
- **평균의 함정**: A가 집계 1위였으나, 그 우위가 식이요법 한 문항에 의해 만들어진 것. 그 문항을 빼면 C가 9/10에서 우세.
- **변수 혼재**: C는 "언어별 크기 + 클렌징"을 한꺼번에 바꿔 무엇이 효과인지 분리 불가.
- **클렌징 부작용**: C의 식이요법 CP=0은 검색 실패가 아니라, 클렌징이 섹션 헤더("국민 암예방 수칙 실천지침")를 지운 탓.

**→ v2로 넘어간 이유**: 평가셋을 키우고(→20, 이후 30), **변수를 하나씩 격리**하는 설계로 재구성.

## 4. v2 — 언어별 청킹 확정

**공통 설계**
- 평가셋: golden_set_v1 (한국어 20 + 영어 10 = 30문항). 영어는 이중언어 검색 검증을 위해 NCCN 문서 근거로 출제.
- 로더: PyMuPDFLoader / 생성: gpt-4o-mini / 채점: Sonnet 5 (1회) / 지표 해석은 Context Precision 중심.

### 4-1. 크기 격자 실험 → G2 채택

**설계**: 진단이 좁혀준 후보로 2×2 격자 구성 (클렌징 off, 크기만 격리).

| 전략 | 한국어 | 영어 |
|---|---|---|
| G1_ko4_en4 | 540/80 | 470/70 |
| G2_ko4_en3 | 540/80 | 620/90 |
| G3_ko3_en4 | 720/110 | 470/70 |
| G4_ko3_en3 | 720/110 | 620/90 |

**결과 (언어별 Context Precision)**

| | 한국어 CP | 영어 CP |
|---|---|---|
| G1 ko4/en4 | 0.624 | 0.687 |
| **G2 ko4/en3** | **0.680** | 0.671 |
| G3 ko3/en4 | 0.616 | 0.719 |
| G4 ko3/en3 | 0.579 | 0.746 |

**핵심 발견**
- **언어별 최적 크기가 반대다**: 한국어는 잘게(ko4)일 때, 영어는 크게(en3~)일 때 검색이 잘 됨. → 진단(한국어가 2.3배 밀도 높음)이 검색에서 실측으로 확인됨.
- **언어별 차등 청킹이 값어치를 한다**: 모든 문서를 같은 크기로 자르는 것보다, 언어마다 다른 크기로 자르는 게 두 언어 검색을 함께 살림.
- **G2가 두 언어 균형 최적**: 한국어 1위(0.680)이면서 영어도 준수(0.671). 이중언어 활용(한국어 질문이 영어 문서 근거도 검색)이 목표이므로, 한 언어만 최적인 config가 아니라 균형점을 채택.

**→ 채택**: G2_ko4_en3 (한 540/80, 영 620/90).

### 4-2. 클렌징 실험 → 기각

**설계**: 4-1에서 확정한 **G2 크기를 고정**하고, 클렌징만 off vs on으로 격리. 클렌징은 위치 기반(페이지 맨 위/아래 반복 머리말·페이지번호)으로 v1의 본문 삭제 실수를 방지.

**결과 (G2 vs G2+클렌징, 동일 크기·동일 judge)**

| 지표 | 클린 off | 클린 on | 델타 |
|---|---|---|---|
| context_precision | 0.677 | 0.615 | −0.062 |
| faithfulness | 0.656 | 0.598 | −0.058 |
| answer_relevancy | 0.904 | 0.870 | −0.034 |

**핵심 발견**
- **클렌징은 검색을 악화시켰다** — 세 지표, 두 언어 모두 하락. 1.00이던 문항 다수가 0.50으로 반토막.
- **원인**: 제거한 반복 머리말(1560줄)에 문서 제목·섹션명 등 **검색 앵커** 역할을 하는 줄이 포함됨. "반복되는 짧은 줄 = 노이즈"라는 직관이 이 데이터에선 성립하지 않음.

**→ 기각**: 반복 머리말은 노이즈가 아니라 맥락 신호로 유지.

## 5. v3 — 로더 비교 → pymupdf4llm 기각

**설계**: v2에서 확정한 청킹(G2, 클렌징 없음)을 고정하고, **로더만** 격리해 비교. 분할기·평가셋은 동일.

| config | 로더 | 청킹 |
|---|---|---|
| L1_pymupdf | PyMuPDFLoader | G2 (한 540/80, 영 620/90) |
| L2_pymupdf4llm | pymupdf4llm (markdown, 표 보존) | G2 (동일) |

- 채점: claude-haiku-4-5 (비용 절감, v2 Sonnet 5와 다름 → v3 내부 비교로만 해석).
- 관전 포인트: 표가 한국어 가이드라인에 집중돼 있으므로(진단), 표 보존 파서의 효과는 주로 한국어 문항에서 나타날 것으로 예상.

**결과**

| 지표 | L1 pymupdf | L2 pymupdf4llm | 델타 |
|---|---|---|---|
| context_precision | 0.696 | 0.506 | −0.190 |
| faithfulness | 0.687 | 0.646 | −0.041 |
| answer_relevancy | 0.839 | 0.807 | −0.032 |
| 평균 chunk 길이(문자) | 477 | 430 | — |

언어별 Context Precision:

| | L1 pymupdf | L2 pymupdf4llm |
|---|---|---|
| 한국어 | 0.758 | 0.522 |
| 영어 | 0.571 | 0.474 |

문항 단위로도 17문항 하락, 6문항만 개선.

**핵심 발견**
- **표 보존이 오히려 검색을 악화시켰다.** 예상과 반대로, 표가 몰린 **한국어에서 가장 크게 하락**(−0.24).
- **원인 1 — markdown 표가 임베딩엔 노이즈**: pymupdf4llm은 표를 `| ... |` markdown으로 추출하는데, 자연어로 학습된 임베딩 모델(e5)은 이 표 마크업을 잘 매칭하지 못함. 검색된 context의 표 기호(`|`) 밀도가 L1보다 약 5배 높았음.
- **원인 2 — chunk 파편화**: markdown 헤더·표 줄이 분할 지점을 늘려 평균 chunk가 짧아짐(477→430). 하나로 있어야 할 답이 여러 조각으로 흩어져 매칭 저하.
- **증거 문항**: "유방암 검진은 몇 살부터?"에서 L1은 정답("40-69세, 2년마다")을 1순위로 검색(CP 1.00)했으나, L2는 무관한 내용(PTEN 유전변이 검진)을 검색(CP 0.00).

**→ 기각**: PyMuPDFLoader 유지. 표 보존 markdown은 자연어 임베딩과 궁합이 나쁘고 chunk를 파편화함.

## 6. 확정 사항 요약

- **청킹 크기**: 언어별 차등 적용 — 한국어 540/80, 영어 620/90 (= G2_ko4_en3).
- **노이즈 제거**: 미적용 (반복 머리말이 검색 앵커라 제거 시 손실 → 기각).
- **로더**: PyMuPDFLoader 유지 (pymupdf4llm 비교 → 표 markdown이 임베딩 노이즈·chunk 파편화로 검색 악화, 기각).
- **평가 기준**: 소규모 평가셋에서 절대 점수 대신 상대 순위 + 문항별 검증 + 언어별 분리 해석.

## 7. 한계 및 메모
- **영어 chunk 크기(470/620)**: 페이지 글자수 추정(1584자) 기반. 정밀 보정은 추후 가능.
- **비용 제약**: v2 클렌징 채점 중 일부(1개 지표/1문항)가 크레딧 소진으로 누락됐으나 결론에는 영향 없음. v3부터 저비용 judge(Haiku)로 전환.
