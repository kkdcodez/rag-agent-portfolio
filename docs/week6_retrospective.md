# Week 6 회고 — LangGraph 기반 Agentic RAG

## 목표

"답할지 말지"의 판단을 LLM의 재량에서 구조의 규칙으로 옮기고, Baseline RAG와 동일한 42문항으로 비교한다.

Week 5까지의 시스템은 검색된 근거가 충분한지를 생성 프롬프트 안에서 LLM이 스스로 판단했다.
Week 6에서는 그 판단을 코드로 분리하고, 판단 결과에 따라 재검색·거절·답변으로 경로를 나눈다.

이번 주차는 **세 단계**를 거쳤다. v1(점수 기반 라우팅) → 검색 설정 불일치 발견 → v3(점수 필터 + LLM 판정).
중간에 발견한 설정 오류가 앞선 실험의 전제를 무너뜨렸기 때문에, 그 과정을 순서대로 기록한다.

## 1. 사전 작업 — 평가셋 재설계

과제 순서상 평가셋 확장은 Week 7 작업이지만 Week 6 앞으로 당겼다.

**이유**
- 기존 30문항에 답변을 거절해야 하는 질문이 하나도 없었다. Agentic RAG의 핵심 기능인 거절·재검색 분기를 평가할 수 없다.
- Week 7에서 확장하면 baseline과 Agentic을 각각 두 번씩 실행해야 한다.

**결과: 30문항 → 42문항 (golden_set_v3)**

| q_type | 문항 수 |
|---|---|
| factual | 20 |
| multi_hop | 6 |
| comparison | 5 |
| out_of_scope | 4 |
| safety | 4 |
| adversarial | 3 |

### 라벨 설계의 변천

처음에는 `expected_behavior`를 answer / refuse / **refer** 3값으로 정의했다.
`refer`는 "근거는 있으나 개인 의료 판단이므로 일반 정보만 제시하고 결정은 넘긴다"는 뜻이었다.

그러나 이 분류가 답변 품질을 제대로 잡아내지 못한다는 문제가 드러났다.
좋은 답변은 "관련 내용을 충분히 설명하고 마지막에 의료진 상담을 안내하는 것"인데,
`refer`를 별도 경로로 두면 "안내만 하고 정보는 주지 않는" 답변도 정답으로 처리된다.

**→ 축을 둘로 분리했다.**

| 컬럼 | 값 | 측정 대상 |
|---|---|---|
| `expected_behavior` | answer(38) / refuse(4) | 라우팅 — 답할까 말까 |
| `needs_referral` | True(4) / False(38) | 답변 품질 — 안내를 붙였나 |

기존 refer 4문항(35·36·37·38)은 `answer` + `needs_referral=True`가 되었다.
시스템 출력(answer/refuse 2값)과 라우팅 라벨이 1:1로 대응하고,
안내 여부는 별도 지표로 측정할 수 있게 되었다.

Week 5에서 정답 라벨이 좁아 더 완전한 답변이 감점됐던 사례(검진 연령 문항)를 반영해,
1번 문항의 ground_truth를 연령대별 권고와 고위험군 기준까지 포함하도록 보강했다.

## 2. 라벨 검증과 임계값 도출

신규 12문항 중 라벨 확인이 필요한 7문항을 생성 없이 검색만 수행해 검증했다
(`notebooks/week6_0_goldenset_check.ipynb`).

목적은 라벨이 실제 문서 상태와 일치하는지 확인하는 것이었으나, 예상하지 못한 결과를 얻었다.

**rerank score가 세 구간으로 분리됐다.**

| 구간 | score | 해당 문항 |
|---|---|---|
| 근거 명확 | 0.92 ~ 0.99 | 37 타목시펜, 39 BRCA1 |
| 부분 관련 | 0.36 ~ 0.43 | 31 최신 임상시험 (시점 불일치) |
| 근거 없음 | 0.03 ~ 0.05 | 32 치료비, 33 병원 순위 |

이 분포를 근거로 `grade` 노드의 임계값을 0.5 / 0.1로 정했다.
0.5는 bge-reranker의 시그모이드 중립점(원본 점수 0)이며, 42문항 분포에서
0.472와 0.821 사이가 비어 있어 경계가 안정적임을 확인했다.

**이 판단의 한계는 나중에 드러났다.** 표본이 7문항이었고, 그 안에
"답이 있는데 검색이 약한 문항"이 하나도 없었다. 성격이 다른 실패가 섞이는 상황이 보이지 않았다.

**부수 발견** — NCCN 문서의 색인(index) 페이지가 chunk로 잔존해 있다.
Week 5 전처리(5-0)는 참고문헌만 제거했다. 페이지 번호 나열뿐이라 내용이 없으며,
34번 문항에서 상위 검색 결과로 올라왔다.

## 4. v1 — 점수 기반 라우팅

```
retrieve → grade(rerank score)
             ├─ ≥ 0.5 → generate
             ├─ < 0.1 → refuse
             └─ 그 사이 → rewrite (최대 2회, 소진 시 generate)
```

### grade에 LLM을 사용하지 않은 이유

baseline 실행에서 qid 4가 프롬프트 한 줄 수정만으로 답변→거절로 반전되는 것을 관찰했다.
LLM 판단의 불안정성이 실패 원인이므로, 해결책에 다시 LLM 판단을 넣지 않기로 했다.
또한 라벨 검증에서 score가 구간을 구분하고 있음이 확인된 상태였다.

### 설계 결정 3가지

| 상황 | 결정 | 근거 |
|---|---|---|
| 재시도 소진 후에도 score가 낮음 | 거절하지 않고 generate | 대상이 answer 문항이므로 거절하면 오답 |
| 재검색 결과가 이전보다 나쁨 | 이전 검색 결과 유지 | Week 5-3 Multi-Query가 정상 검색을 악화시킨 사례 |
| 거절 문구 | 질문 언어에 맞춘 고정 문구, LLM 호출 없음 | 응답 속도 유지, 영어 질문의 한국어 거절 문제 해결 |

### v1 결과

| expected_behavior | answer | refuse |
|---|---|---|
| answer (34) | 34 | 0 |
| refer (4) | 3 | 1 |
| refuse (4) | 2 | 2 |

재시도: 0회 37문항 / 1회 1문항 / 2회 4문항. **오거절 0건.**

**재검색을 탄 5문항의 실제 성과**

| qid | score 변화 | 판정 |
|---|---|---|
| 4 | 0.150 → 0.494 | **개선** — 거절에서 병기 분류 답변으로 |
| 36 | 0.472 → 0.811 | 점수만 상승, 답변 내용은 baseline과 동일 |
| 10 | 0.127 → 0.235 | 동등 |
| 31 | 0.433 → 0.479 | 무효 — 문서에 답이 없음 |
| 34 | 0.364 → 0.428 | 무효 — 문서에 답이 없음 |

**재검색 5건 중 실질 개선은 1건.** 나머지 4건은 지연만 2.5배 증가시켰다
(3.24초 → 7.97초). 31·34는 out_of_scope 문항이므로 재검색 자체가 낭비였다.

36번은 처음에 개선 사례로 기록했으나, 답변 텍스트를 직접 대조한 결과
baseline과 표현만 다르고 내용이 같았다. **점수 상승이 답변 개선을 뜻하지 않는다**는
Week 5의 관찰이 다시 확인된 사례다.

### v1이 드러낸 구조적 한계

0.5 미만 8문항을 다시 보면 문제가 분명해진다.

| qid | score | 문서에 답이 있나 |
|---|---|---|
| 38 | 0.027 | 일부 있음 |
| 32 | 0.030 | 없음 |
| 33 | 0.052 | 없음 |
| 10 | 0.127 | **있음** |
| 4 | 0.150 | **있음** |
| 34 | 0.364 | 없음 |
| 31 | 0.433 | 없음 |
| 36 | 0.472 | **있음** |

**답이 없는 31·34(0.36~0.43)가 답이 있는 4·10(0.13~0.15)보다 점수가 높다.**
원하는 순서와 반대로 배열되어 있으므로, 어디에 선을 그어도 두 종류가 갈리지 않는다.

원인은 명확하다. **rerank score는 "관련도"를 재는데, 우리는 "답변 가능성"을 물었다.**
리랭커가 보지 못하는 것이 셋 있다.

- 시점 (최신 정보 요구인지)
- 근거의 합 (조각 5개를 합치면 답이 되는지 — v1은 1등 점수만 사용)
- 질문의 성격 (사실 조회인지 조언 요청인지)

**→ 임계값 조정으로는 해결할 수 없다는 결론.**

## 5. 검색 설정 불일치 발견 — 이번 주차의 최대 사건

v1 결과를 분석하던 중, qid 4가 Week 5에서는 정확히 답했다는 사실을 확인했다.
Week 5 결과 CSV에는 ESMO p.17의 병기 분류 표 전문이 1순위로 검색되어 있었고,
Faithfulness 0.875 / Context Precision 1.0이었다.

Week 6에서는 같은 질문의 최고 점수가 0.150이었다. 동일한 R4 구성이라고 기록해 두었으므로
이 차이는 설명되지 않는다.

### 추적 과정

**가설 A — 전처리가 표를 지웠는가** → 기각.
전처리 전(P0)과 후(P1) 인덱스를 대조한 결과 병기 표 chunk가 양쪽 모두에 동일하게 존재했다
(ESMO p.17 505자, KBCS p.58 532자).

**가설 B — 청킹 경계가 밀렸는가** → 기각. 위와 동일.

**가설 C — 검색이 못 찾는가** → 확인됨.

```
정답 chunk(1162)   RRF 후보 20개에 없음 · rerank 점수는 0.866
실제 선택된 chunk   RRF 2위 · rerank 점수 0.145
```

정답 chunk는 리랭커가 0.866을 줄 만큼 적합했으나, 1차 검색 후보에 들지 못해
리랭커가 볼 기회조차 없었다.

**후보 수를 늘려도 dense는 찾지 못했다.**

```
n=30   dense 없음 / bm25 없음
n=100  dense 없음 / bm25 97위
n=300  dense 없음 / bm25 97위
```

### 원인 — 모듈화 과정에서 설정을 임의로 변경했다

Week 5 노트북 원본과 대조한 결과 세 곳이 달랐다.

| 항목 | Week 5 확정값 | Week 6 코드 | 출처 |
|---|---|---|---|
| BM25 토큰화 | **내용어만** (N/V/S, SL/SN/XR) | 전체 토큰 | decision_log W5에 명시 |
| Dense 질의 | 원문 그대로 | **"query: " prefix 추가** | week5_0 cell 17 (인덱싱 시 prefix 미사용) |
| 1차 후보 수 | 20 (FETCH_K) | 30 | week5_2 cell 2 |

**BM25 토큰화가 결정적이었다.** 조사·어미를 포함하면 "와, 의, 는, 이" 같은 고빈도 토큰이
거의 모든 chunk에 존재해 `유방암`, `1기`, `2기`, `차이` 같은 실제 신호를 희석시킨다.
병기 표는 조사가 적은 표 형태이므로 상대적으로 더 불리해져 97위까지 밀렸다.

Dense prefix는 인덱싱 시 `passage:`를 쓰지 않았는데 질의에만 `query:`를 붙여
벡터 공간이 어긋난 경우다.

decision_log에 "BM25 토큰화 = kiwipiepy 형태소(내용어만)"이 명시되어 있었고,
"5주차 최종 구성을 그대로 사용"이라고 문서에 기록했으나 사실이 아니었다.

### 수정과 검증

`retrieval.py`를 Week 5 노트북 함수와 1:1로 대응하도록 다시 작성하고,
각 함수에 출처 노트북과 셀 번호를 주석으로 명시했다.

```
수정 후
  chunk 1162   RRF 17위 → rerank 0.866 → 최종 1위
  최고 점수    0.150 → 0.866
  답변         "확인할 수 없습니다" → T1N0M0/T2N0M0 병기 분류 정확히 설명
```

리랭커가 1차 검색 17위 chunk를 내용 기반으로 1위까지 올렸다.
Week 5 회고의 "Rerank는 무엇을 찾는가가 아니라 무엇을 위에 놓는가를 바꾼다"가 재현됐다.
동시에 **17위는 후보 20개 문턱에 아슬아슬하다**는 취약성도 드러났다.

**인덱스 검증** — 4주차 결정이 인덱스에 반영되어 있는지 별도로 확인했다.

| 4주차 결정 | 확인값 | |
|---|---|---|
| 한국어 540/80 | 최대 540자, 평균 444자, 1,112 chunk | ✅ |
| 영어 620/90 | 최대 620자, 평균 520자, 1,128 chunk | ✅ |
| PyMuPDFLoader (pymupdf4llm 기각) | 표 markdown 의심 chunk 0개 | ✅ |
| 클렌징 미적용 | 총 2,240 chunk (= Week 5 P1) | ✅ |

인덱스 층은 4·5주차 실험 결과 그대로였다. 훼손된 것은 검색 코드 한 층뿐이었다.

한국어 chunk 평균 444자(최대의 82%), 영어 520자(84%)로 두 언어의 충전율이 비슷하고,
원본 페이지 수가 한국어 466 / 영어 330으로 차이가 큼에도 chunk 수는 1,112 / 1,128로 균형을 이뤘다.
4주차의 언어별 차등 청킹이 의도대로 작동하고 있음을 확인했다.

### 이 사건의 교훈

**집계 평균으로는 발견할 수 없는 오류였다.** 42문항 중 점수가 바뀐 문항이 3개뿐이고,
그중 유의미한 것은 qid 4 하나였다. 전체 평균은 거의 변하지 않는다.

| qid | 수정 전 | 수정 후 |
|---|---|---|
| 4 comparison | 0.150 | **0.866** |
| 19 adversarial | 0.875 | 0.915 |
| 33 out_of_scope | 0.052 | 0.042 |
| 나머지 39문항 | — | 변화 없음 |

Week 4의 "평균의 함정" 이후 지켜온 문항 단위 검증과, 이전 주차 결과 CSV를 보존해 온 것이
발견의 조건이었다.

**재발 방지**
- 모든 설정값에 출처(노트북·셀 번호)를 주석으로 명시
- 이전 주차 구성을 재사용할 때는 항목별 대조표를 먼저 작성
- 이전 주차에서 성공한 문항으로 재현 검증 수행

## 6. v3 — 점수는 필터, 판정은 LLM

v1의 구조적 한계(점수가 관련도만 측정)에 대응해 역할을 나누었다.

```
retrieve → filter(rerank score)
             ├─ ≥ 0.5 → generate                (LLM 호출 없음)
             └─ < 0.5 → judge (LLM)
                          ├─ answer  → generate
                          ├─ refuse  → refuse
                          └─ rewrite → 재검색 (최대 2회, 소진 시 answer)
```

**v1의 0.1 선을 제거했다.** 그 아래로 떨어진 문항이 판정 기회 없이 즉시 거절되어,
일반 정보가 존재하는 질문(qid 38)이 고정 문구만 받았기 때문이다.

### 판정자 설계

**입력** — 원 질문, 현재 검색어, 질문 언어, 재검색 횟수, 조각 5개 전문, 조각별 점수, 조각별 출처

평가셋 라벨(q_type, expected_behavior)은 **의도적으로 차단**했다. 실제 서비스에 존재하지 않는
정보이므로, 이를 주면 평가 점수는 오르지만 재현되지 않는다.

문서 기준 연도를 별도로 주는 방안은 채택하지 않았다. 특정 문항에 맞춘 설계가 되어
문서가 추가되면 작동하지 않는다.

**판정 정책의 핵심**

> refuse는 되돌릴 수 없다. 생성 단계에 "근거 없으면 확인할 수 없다고 답하라"는 규칙이
> 있으므로 잘못된 answer는 회복되지만, 잘못된 refuse는 회복되지 않는다.

따라서 refuse에는 "범위 밖임을 적극적으로 입증하는 근거"를 요구하고,
다음은 refuse의 근거가 되지 않는다고 명시했다.

- 지금 조각에 답이 없다
- rerank 점수가 낮다
- 질문이 요구한 시점의 자료를 찾지 못했다
- 개인 상황에 대한 확정적 판단을 내릴 수 없다

### rewrite / refuse 구분 축을 바꾼 과정

초기 프롬프트는 rewrite를 "문서에 답이 있을 것 같지만 현재 조각에는 없다"로 정의했다.
그러나 판정자는 검색된 5개 조각만 보므로 "문서 어딘가에 있는가"를 알 수 없다.

**8문항 테스트에서 rewrite가 0회 선택되었고, qid 4가 오거절되었다.**
판정 사유는 "현재 검색된 조각에는 1기와 2기의 차이에 대한 정보가 없다"로 사실이었으나,
그때 골라야 할 것은 refuse가 아니라 rewrite였다.

판정자가 실제로 볼 수 있는 축으로 바꾸었다.

> 질문이 요구하는 정보의 **종류**가 이 문서 모음이 다루는 종류인가?

- in_scope — 다루는 주제이나 이번 검색이 못 찾았을 수 있다 → rewrite
- out_of_scope — 비용, 기관 평가, 개인 기록, 실시간 정보 등 → refuse

### 출력 순서를 강제했다

`asked → evidence → category → reason → decision` 순으로 출력하며 decision이 마지막이다.

초기 버전에서 판정자가 결론을 먼저 내고 사유를 사후 생성하는 현상이 관찰되었다.
qid 31에서 "여러 조각을 종합하면 2025년 이후 발표된 HER2 표적치료제의 최신 임상시험 결과에 대한
정보를 제공할 수 있다"는 **사실과 다른 사유**를 생성했다.

순서를 바꾼 뒤 같은 문항의 사유가 "검색된 조각에서 HER2 양성 전이성 유방암에 대한 최근 임상시험
결과가 일부 포함되어 있다"로 바뀌었다. 결론은 여전히 answer지만 거짓 근거는 사라졌다.

### 재작성 검색어를 판정자가 직접 생성한다

무엇이 부족했는지 판단한 주체가 검색어도 만드는 편이 정확하고, LLM 호출이 1회 줄어든다.
원 질문의 시점·대상군·비교 조건을 삭제하지 않는다는 규칙을 명시했다.

## 9. 남은 문제

### ① 라우팅과 생성에 판단이 이중으로 존재한다

판정자가 answer로 보내도 생성 프롬프트의 규칙("근거 없으면 확인할 수 없다고 답하라")이
다시 거절을 판단한다.

**qid 38이 대표 사례다.**

```
판정: answer/partial — "치료 주기에 관한 일반 정보는 있으나
                        건너뛰기 여부를 직접 다루지는 않는다"   (정확한 판단)
검색: 조각 [1]에 "다음 주기 전 몸이 회복할 시간을 준다" 내용 존재

Baseline 답변: 일반 정보 제시 + "care team과 상의하라" 안내
Agentic 답변:  "제공된 문서에서 확인할 수 없습니다."   ← 안내 없음
```

**판정자가 옳게 통과시켰는데 생성 단계가 거절했고, 결과적으로 baseline보다 나빠졌다.**
판단 지점이 두 곳이라 동작을 예측하기 어렵다.

qid 30, 37도 `expected_behavior=answer`인데 거절 표현이 포함되어 있다.

### ② 생성 결과가 결정적이지 않다

temperature=0이지만, **검색 결과가 완전히 동일한 42문항 중 27문항에서**
baseline과 Agentic의 답변 문장이 달랐다.

내용상 오류는 없으나, 이 변동 폭이 구조 차이보다 크다.
Week 7에서 RAGAS 점수가 0.02~0.03 차이로 나올 경우, 그것이 구조 개선인지
생성 변동인지 구분할 수 없다.

### ③ 시점 조건 판단 — RAG 구조의 한계로 이월

"2025년 이후 발표된" 같은 시점 조건은 판정자가 검증할 수 없다.
검색된 5개 조각만으로는 코퍼스 전체에 해당 시점 자료가 없다는 것을 알 수 없기 때문이다.

코퍼스 메타데이터(최신 문서 일자)를 입력에 추가하는 방안을 검토했으나,
확인 결과 본 코퍼스에는 2025년판 NCCN 문서가 포함되어 있어
"최신 일자 = 2025"가 되므로 qid 31을 판별하지 못한다.

**정적 문서 인덱스의 구조적 한계다.** 웹 검색 도구나 문서 갱신 파이프라인이
있어야 해결되므로 Phase 2 과제로 이월한다.

### ④ 색인 페이지 chunk 잔존

Week 5 전처리는 참고문헌만 제거했다. NCCN 문서의 색인 페이지는 페이지 번호 나열이라
내용이 없으면서 검색 결과 상위에 올라올 수 있다.

## 11. 이번 주차의 교훈

**① 점수는 필터로는 유효하지만 판단 기준으로는 부족하다**

rerank score는 42문항 중 35문항을 즉시 정확히 통과시켰다. 비용 0, 지연 0의 필터로서
값어치가 있다. 그러나 0.5 미만 구간에서 "답할까 거절할까"를 결정하는 데 쓰자
관련도와 답변 가능성을 구분하지 못했다. 도구를 잘하는 일에만 쓰는 것이 구조를 안정시킨다.

**② 실험으로 확정한 값은 사양이지 권장사항이 아니다**

모듈화 과정에서 세 개의 설정을 임의로 변경했고, 그중 하나는 decision_log에 명시되어 있던
항목이었다. 그 결과 Week 6 실험 두 세트를 폐기하고 재실행해야 했다.

특히 Dense prefix는 "e5 모델은 prefix를 쓴다"는 일반 지식으로 판단한 것이다.
이 프로젝트가 4주차부터 반복해서 증명한 것이 "일반적으로 좋다는 것이 우리 데이터에서는
아니다"였는데, 정확히 그 실수를 반복했다.

**③ 문항 단위 검증이 오류를 잡았다**

설정 불일치로 실제 점수가 바뀐 문항은 42개 중 3개였고, 전체 평균은 거의 변하지 않았다.
집계만 봤다면 Week 8 freeze까지 발견되지 않았을 것이다.

**④ 실패한 구현도 기록으로 남긴다**

v1(점수 라우팅)은 폐기됐지만, "왜 점수만으로는 안 되는가"를 수치로 보여주는 근거다.
v3의 설계 근거가 v1의 실패 데이터에 있다.
